## 待决问题与选项清单

### 问题 1：注册表开机启动项的安全性与未加引号路径加固 (Security)
- **背景**：当前 `SetAutostart` 在写入 `HKCU\...\Run` 时未对可执行文件路径添加双引号，当路径包含空格时存在未加引号启动路径（Unquoted Search Path）劫持风险。
- **选项 A（推荐）**：严格格式化添加双引号 `\"%s\" %s`
  - **优势**：改动最小、精准解决 Windows 路径空格歧义安全问题，保持与现有参数 `--autostart` 机制完全兼容。
  - **劣势**：仍然使用注册表 Run 键，无法支持更复杂的计划任务权限控制（不过作为普通用户工具已完全足够）。
- **选项 B**：迁移到 Windows 任务计划程序（Task Scheduler API）自启
  - **优势**：支持以更高权限/延迟启动、提供更丰富触发器与自愈能力。
  - **劣势**：需要链接额外 COM/TaskScheduler 依赖，增加代码体积与调用复杂度，小工具过度设计。
- **选项 C**：仅在路径确实包含空格时动态添加引号
  - **优势**：按需加引号。
  - **劣势**：增加分支判断与测试盲区，无条件统一加双引号是 Windows API 标准最佳实践。
- **用户选择**：`选项 A`
- **选择理由/备注**：采用严格格式化双引号包裹可执行文件路径（`\"%s\" %s`），精准消除未加引号路径劫持漏洞，保持零依赖与轻量注册表实现。

### 问题 2：FanControl 外部进程调用的安全性与参数注入防护 (Security)
- **背景**：当前使用 `ShellExecuteW(NULL, L"open", g_fanControlExe, args, NULL, SW_HIDE)`，`args` 采用字符串拼接 `L"-c \"%s\""`，存在特殊字符跳出引号参数注入的风险，且 `ShellExecuteW` 不适合纯子进程调用。
- **选项 A（推荐）**：改用 `CreateProcessW` + 严格参数转义与路径合法性校验
  - **优势**：绕过系统 Shell 关联和协议解析，直接创建进程；对 `-c` 后的 JSON 路径进行引号转义和文件存在性检查，安全边界最高，能精确处理进程创建错误。
  - **劣势**：需要构造 `STARTUPINFOW` / `PROCESS_INFORMATION` 并妥善关闭 `hProcess` 和 `hThread` 句柄。
- **选项 B**：保留 `ShellExecuteW`，仅增加参数转义与路径去引号清洗
  - **优势**：代码改动少。
  - **劣势**：`ShellExecuteW` 依然会走 Shell 解析链，错误处理能力不如 `CreateProcessW` 精确。
- **选项 C**：改用 Windows 命名管道/IPC（若 FanControl 未来开放）或原生消息
  - **优势**：无需每次启动新进程通知 FanControl。
  - **劣势**：FanControl 官方公开支持的外部切换配置方式就是 `-c` 命令行参数，没有官方稳定的 IPC 管道。
- **用户选择**：`选项 A`
- **选择理由/备注**：改用 Win32 原生 `CreateProcessW`，严格校验配置文件与 exe 路径存在性，并对命令行参数进行标准转义，彻底杜绝参数注入并获得精准的错误诊断。

### 问题 3：单文件上帝代码与全局状态的架构重构方式 (Architecture)
- **背景**：当前 `fan_hotkey.c` 1300 行将 UI、配置、热键、轮询监控、Win32 窗口全部塞在单文件，全局暴露 30+ 静态变量。
- **选项 A（推荐）**：多文件清晰模块化 + `AppContext` 显式上下文结构体
  - **优势**：按职责拆分 `app_context.h`、`config.c/.h`、`hotkey.c/.h`、`process_monitor.c/.h`、`ui_main.c`、`ui_settings.c`；消除隐式全局变量，方便后续单测与维护。
  - **劣势**：编译时需要编译多个 `.c` 文件，头文件依赖关系需理清。
- **选项 B**：保留单文件结构，但在文件内做显式分层与 `AppContext` 聚合
  - **优势**：继续保持单文件编译便利性，零头文件管理负担。
  - **劣势**：单文件行数仍然较大，无法彻底实现模块物理隔离与单独单元测试。
- **选项 C**：引入微型组件/事件驱动框架（Event Bus 机制）
  - **优势**：各模块彻底解耦，通过事件收发消息。
  - **劣势**：对于 1000 多行的小工具严重过度设计（Over-engineering），增加调用链追踪难度。
- **用户选择**：`选项 A`
- **选择理由/备注**：按功能职责进行多文件模块化拆分，定义统一的 `AppContext` 结构体进行显式上下文传递，彻底消除全局静态变量污染，使纯业务逻辑与 Win32 GUI 解耦。

### 问题 4：设置窗口与业务模型的事务隔离（草稿/Draft 机制） (Architecture)
- **背景**：当前在设置界面增删进程名是直接操作全局 `g_modes`，点击 Cancel 只能强行调用 `LoadConfig()` 从磁盘恢复，且未重置主窗口与热键状态，存在数据不一致。
- **选项 A（推荐）**：设置窗口打开时深拷贝生成 `ConfigDraft`，点击 OK 才原子提交并应用
  - **优势**：UI 交互完全在 Draft 上进行，Cancel 时直接丢弃 Draft 即可，零磁盘 I/O，不污染运行态；点击 OK 时原子更新并触发热键与主窗口刷新。
  - **劣势**：需要编写配置深拷贝（`Config_Clone` / `Config_Apply`）逻辑。
- **选项 B**：Cancel 时记录操作反向撤销栈（Undo Log）
  - **优势**：能够支持多步 Undo。
  - **劣势**：实现复杂度极高，极易遗漏边缘情况。
- **选项 C**：保留直接修改 `g_modes`，但在 Cancel 读盘恢复后补齐主窗口与热键刷新
  - **优势**：改动最小（仅补加刷新调用）。
  - **劣势**：在用户打开设置窗口但尚未点击 OK 期间，后台 2 秒定时器仍会读取到用户半途修改的脏数据。
- **用户选择**：`选项 A`
- **选择理由/备注**：设置窗口引入独立的 `ConfigDraft` 事务草稿机制，所有编辑操作仅在内存草稿中进行，Cancel 干净丢弃，OK 原子生效，彻底消除脏读与竞态。

### 问题 5：字符串字符集编码与内部内存模型 (Performance & Readability)
- **背景**：目前应用启用了 Unicode 宏，但内部结构体 `Mode` 却存 `char` (UTF-8)，导致全篇大量 `Utf8ToWide` / `WideToUtf8`，定时器内层热路径也在重复转码。
- **选项 A（推荐）**：全工程内部统一使用原生 `wchar_t` (UTF-16)，仅在 INI/文件 I/O 边界处理
  - **优势**：与 Win32 原生 API 100% 契合，彻底移除热路径和 UI 层的数十处编解码胶水代码，代码更简洁、性能更优。
  - **劣势**：需要重构 `Mode` 结构体及配置读写函数中的字符串类型。
- **选项 B**：继续保持内部 UTF-8 存储，但在 `Mode` 中增加宽字符缓存字段
  - **优势**：对现有结构体定义改动较小。
  - **劣势**：存在数据双份存储与同步维护成本，治标不治本。
- **选项 C**：将整个项目改用 ANSI / MBCS（`char`）API
  - **优势**：无需转码。
  - **劣势**：严重倒退，在多语言路径（中文路径、特殊字符）下必然产生乱码和路径找不到的问题。
- **用户选择**：`选项 A`
- **选择理由/备注**：项目内部全面统一采用 Win32 原生 `wchar_t` 宽字符模型，彻底消除各层之间的转码胶水代码与热路径转码开销，保障中文和特殊字符路径的绝对稳定性。

### 问题 6：进程感知自动切换的检测算法与性能优化 (Performance)
- **背景**：当前每 2 秒调用 `CreateToolhelp32Snapshot` 全量枚举系统 1024 个进程，并用三重嵌套循环进行 `_wcsicmp` 字符串比对。
- **选项 A（推荐）**：保留定时快照，但改用哈希集合（HashSet / FNV-1a）或快照排序 + 二分查找
  - **优势**：将比对复杂度从 $O(Modes \times ProcList \times RunningProcs)$ 降至 $O(1)$ 或 $O(\log N)$；保持实现轻量且兼容所有 Windows 版本。
  - **劣势**：仍然存在每 2 秒一次的快照开销（但对现代 CPU 而言极其微弱）。
- **选项 B**：改用 Windows 事件钩子（`SetWinEventHook` 监听 `EVENT_OBJECT_CREATE` / `EVENT_SYSTEM_FOREGROUND`）
  - **优势**：零轮询、完全事件驱动。
  - **劣势**：`EVENT_OBJECT_CREATE` 会频繁触发（系统每创建一个 UI 元素就触发），过滤噪音成本高；无法直接拿到新进程可执行文件名。
- **选项 C**：改用 WMI / ETW 进程启动事件跟踪
  - **优势**：精准捕捉进程创建与退出。
  - **劣势**：需要引入庞大的 COM/WMI 依赖或管理员权限，对轻量级小工具过于沉重。
- **用户选择**：`选项 A`
- **选择理由/备注**：保留定时快照采集，内部引入高效哈希查找（FNV-1a / 大小写不敏感哈希），将多重嵌套循环复杂度降至 $O(1)$，在保持轻量无依赖的同时获得最优执行性能。

### 问题 7：高 DPI 屏幕支持与 Win32 UI 布局方式 (Readability & UX)
- **背景**：当前界面使用硬编码像素坐标（如 `y += 26`, `ry += 74`），缺少 DPI-Awareness 声明，在高分辨率缩放屏下容易模糊或截断。
- **选项 A（推荐）**：添加 DPI-Awareness Manifest + 基于 DPI Scale 动态缩放辅助函数（`ScaleDpi(val)`）
  - **优势**：原生高清不模糊；保留手动绝对坐标的高控制力，同时通过 `ScaleDpi(x)` 自动按当前屏幕 DPI（100%、125%、150%、200%）等比缩放。
  - **劣势**：需要在 `resource.rc` 中嵌入 manifest，并在创建窗口时计算 DPI。
- **选项 B**：重构为标准 Windows 对话框模板（Dialog Template / `.rc` 对话框资源）
  - **优势**：系统自动处理部分基于对话框基础单元（DLU）的缩放。
  - **劣势**：Win32 对话框资源维护繁琐，动态逻辑与控件状态绑定不够灵活。
- **选项 C**：不做 DPI 缩放，仅声明 `DPI_AWARENESS_CONTEXT_SYSTEM_AWARE`
  - **优势**：改动仅需一行代码。
  - **劣势**：多显示器切换（Per-Monitor）时仍然会被系统拉伸模糊。
- **用户选择**：`选项 A`
- **选择理由/备注**：嵌入标准 DPI-Awareness 应用程序清单（Manifest），并在 UI 初始化与布局时通过统一的 DPI 缩放辅助函数（`ScaleDpi`）进行等比缩放，实现高分屏下原生清晰渲染与自适应布局。

### 问题 8：构建系统与脚本管理 (Engineering)
- **背景**：当前仅在 README/AGENTS.md 里有一段写死本地路径的 PowerShell 命令，缺少通用构建脚本。
- **选项 A（推荐）**：提供 `Makefile` + PowerShell 构建脚本 `build.ps1` 双支持
  - **优势**：`Makefile` 适合标准命令行与 CI/CD；`build.ps1` 适合 Windows 本地一键构建（自动探测或支持指定 MinGW 路径），兼顾各种开发习惯。
  - **劣势**：需要维护两个小构建文件。
- **选项 B**：引入 `CMakeLists.txt`
  - **优势**：跨 IDE（VS Code, CLion, Visual Studio）支持好。
  - **劣势**：为纯 C 的小型 Win32 工具引入 CMake 增加了额外工具链依赖。
- **选项 C**：仅提供 `build.ps1` 单个脚本
  - **优势**：极简，纯 Windows 原生体验。
  - **劣势**：Linux/CI 交叉编译或跨平台工具链调用不够友好。
- **用户选择**：`选项 A`
- **选择理由/备注**：提供 `Makefile` 和 `build.ps1` 双重构建支持，既满足 Windows 本地一键无痛编译，又适配 CI 持续集成环境。

### 问题 9：单元测试与逻辑验证体系 (Engineering)
- **背景**：目前工程 0 个测试，重构快捷键解析、配置序列化、进程去重时无法自动化验证。
- **选项 A（推荐）**：构建基于无依赖微型纯 C 测试框架（如 `minctest` 或纯断言 harness）的独立测试可执行文件（`tests/test_main.c`）
  - **优势**：零第三方依赖、编译速度极快（毫秒级）；专门测试 `ParseHotkey`、`ParseProcessList`、配置读写、DPI 计算等纯逻辑。
  - **劣势**：无法直接自动化测试 Win32 GUI 窗口渲染（但核心业务逻辑已完全覆盖）。
- **选项 B**：引入 GoogleTest / Catch2
  - **优势**：断言和测试报告丰富。
  - **劣势**：需要 C++ 编译器和庞大库依赖，破坏纯 C 项目的一致性。
- **选项 C**：不编写单元测试，仅依靠手动运行 GUI 验收
  - **优势**：开发省时。
  - **劣势**：缺乏回归保障，容易引入隐蔽 Bug。
- **用户选择**：`选项 A`
- **选择理由/备注**：采用零依赖的纯 C 微型单元测试 Harness（`tests/test_main.c`），实现对热键解析、进程列表分析、哈希匹配、配置读写等核心逻辑的毫秒级自动化回归验证。

### 问题 10：CI/CD 持续集成流水线配置 (Engineering)
- **背景**：当前无 GitHub Actions，无法在提交/PR 时自动构建与测试。
- **选项 A（推荐）**：配置 GitHub Actions 工作流（Windows + MinGW-w64 自动编译、跑测试、并在打 tag 时自动发布 Release 二进制）
  - **优势**：全自动化验证、一键产出 Release zip 包与可执行文件，极大提升开源项目工程成熟度。
  - **劣势**：需要增加 `.github/workflows/build.yml` 文件。
- **选项 B**：仅配置 CI 编译与测试校验，不自动打包 Release
  - **优势**：工作流简单。
  - **劣势**：发版时仍需手动本地打包上传。
- **选项 C**：暂不配置 GitHub Actions
  - **优势**：仓库文件最少。
  - **劣势**：无法保证远端构建可重现性。
- **用户选择**：`选项 A`
- **选择理由/备注**：引入 GitHub Actions 持续集成工作流，在代码提交与 PR 时自动拉取 MinGW 编译并运行单元测试，打 Tag 时自动打包生成 Release 构件与 Zip 资产。

## 决策冲突与合理性检查规则
1. **字符集一致性**：若问题 5 选 A（原生 `wchar_t`），则问题 2（`CreateProcessW`）与问题 9（单测）均需直接使用宽字符接口。
2. **架构与事务一致性**：若问题 3 选 A（多文件模块化），则问题 4（Draft 机制）与问题 9（独立单测）可天然无缝对接。
3. **构建与 CI 一致性**：若问题 8 选 A（`Makefile` + `build.ps1`），CI 流水线可直接复用 `make` 或 `build.ps1` 避免重复逻辑。
